# ВышКат — система учёта имущества кикшеринга

Проект представляет собой небольшую систему учёта имущества сервиса проката «ВышКат». В парке могут находиться разные виды транспорта, а также дополнительное оборудование - например, шлемы и зарядные станции.

Основная задача программы - упростить приёмку и учёт имущества. При добавлении транспорта выполняется технический осмотр, а после успешной проверки объект попадает в общий список. Пользователь может посмотреть количество имущества, суммарное энергопотребление и выбрать транспорт, подходящий для новичков.

## Возможности
- Приём транспорта после технического осмотра
- Учёт электросамокатов, велосипедов и электровелосипедов
- Учёт шлемов и зарядных станций
- Проверка уникальности инвентарных номеров
- Подсчёт количества транспортных средств и вещей
- Расчёт суммарного суточного энергопотребления
- Подбор транспорта для новичков (простота управления от 6 до 10)
- Вывод полного списка имущества
- Интерактивное управление через консоль

## Архитектура
Независимые компоненты:
- **domain** — модели имущества и интерфейсы
- **inspection** — технический осмотр транспорта
- **fleet** — бизнес-логика управления парком
- **console** — пользовательский интерфейс
- **app** — создание и связывание зависимостей

В проекте также используется композиция структур, интерфейсы и внедрение зависимостей

## Принципы SOLID

При разработке я старалась разделить программу на небольшие компоненты, чтобы каждый отвечал за свою задачу.

- **SRP:** работа с пользователем вынесена в `ConsoleApp`, учёт имущества - в `FleetService`, а технический осмотр - в отдельный сервис.
- **OCP:** при расчёте энергопотребления программа работает с интерфейсом `EnergyConsumer`, поэтому для нового типа оборудования не потребуется переписывать сам расчёт.
- **LSP:** самокаты, велосипеды и электровелосипеды реализуют интерфейс `Transport` и могут обрабатываться через него.
- **ISP:** вместо одного большого интерфейса используются несколько небольших. Например, велосипеду не нужно реализовывать метод расчёта энергопотребления.
- **DIP:** `FleetService` получает сервис техосмотра через конструктор. Это позволяет заменить реальную проверку на тестовую, не изменяя код самого сервиса.

Для связывания компонентов используется простой DI-контейнер в пакете `app`. Сторонние библиотеки для этого не понадобились. В тестах вместо стандартного сервиса техосмотра можно передать `fakeChecker`, что позволяет проверять работу `FleetService` независимо от реальной проверки транспорта

## Наиболее явный примененный принцип SOLID
Наиболее явно в проекте применяется DIP (Dependency Inversion Principle).
В internal/fleet/service.go сервис FleetService зависит от интерфейса ServiceCenter, а не от конкретной реализации техосмотра. Объект техосмотра передаётся в конструктор NewFleetService.
Это позволяет менять реализацию проверки транспорта без изменения логики управления парком. Например, в тестах вместо StandardServiceCenter используется fakeChecker.

## Принцип SOLID, который сознательно ограничен
Не полностью реализован OCP (Open/Closed Principle) на уровне консольного интерфейса.
Если добавить новый вид транспорта, придётся дополнить меню и обработку пользовательского ввода в internal/console/input.go.
При этом основная бизнес-логика FleetService менять не потребуется, если новый транспорт реализует интерфейс Transport.
Для учебного проекта такое ограничение приемлемо, тк отдельная система регистрации типов и фабрик усложнила бы код без существенной пользы.

## Что изменится при расширении программы
Например, при добавлении нового вида транспорта потребуется создать новую структуру в пакете domain, реализовать интерфейс Transport и добавить соответствующий вариант ввода в console.
Методы подсчёта имущества, фильтрации транспорта для новичков и технического осмотра смогут работать с новым объектом через существующие интерфейсы.
Если добавить сотрудников, потребуется отдельная модель, поскольку по условиям задачи сотрудники не ставятся на баланс. Поэтому включать их в InventoryItem было бы неправильно.
Для склада запчастей можно создать отдельный сервис учёта. При этом существующий FleetService не обязательно изменять.

## Какие тесты проверяют техосмотр и правило для новичков
В internal/fleet/service_test.go тест TestInspectionRejected проверяет, что транспорт не попадает в парк, если техосмотр возвращает ошибку. Для этого используется fakeChecker, который реализует интерфейс ServiceCenter. Он позволяет управлять результатом проверки независимо от реального сервиса.
Тест TestForBeginners проверяет, что в список транспорта для новичков попадают только объекты с показателем простоты управления от 6.
В internal/inspection/service_center_test.go отдельно проверяются успешный техосмотр и отказ при превышении лимита энергопотребления

## Технический осмотр
Технический осмотр в проекте реализован как проверка характеристик транспортного средства. Для энергопотребляющего транспорта контролируется установленный лимит суточного энергопотребления. Программа не проверяет реальное техническое состояние транспорта, а оценивает его по заданным характеристикам.

## Тестирование

Для запуска всех тестов:

```bash
go test ./... -v -count=1
```

Для статической проверки:

```bash
go vet ./...
```

Реализованы 25 автоматических тестов, проверяющих создание объектов, работу парка, технический осмотр, обработку пользовательского ввода и внедрение зависимостей. Общее покрытие тестами составляет 74,7%.

## Пример работы

Допустим, нужно добавить в парк электросамокат Ninebot.

В главном меню выбираем команду `1` - добавление транспорта. Затем указываем тип транспорта, инвентарный номер и характеристики:

```text
Вид транспорта:
1. Электросамокат
2. Велосипед
3. Электровелосипед

Выберите вид: 1
Инвентарный номер: SC-001
Название: Ninebot
Простота управления (1-10): 8
Энергопотребление (кВт·ч/сутки): 1.5

Транспорт успешно принят в парк
```

Теперь при выборе команды `3` программа покажет:

```text
Транспорт: 1, вещи: 0
```

Этот самокат также появится в списке транспорта для новичков, поскольку его простота управления равна 8.

Если попытаться повторно добавить объект с номером `SC-001`, программа сообщит об ошибке. Таким образом, один инвентарный номер не может принадлежать нескольким объектам.

## Особенности реализации

Программа работает в консоли и хранит данные в памяти во время запуска. После завершения работы список имущества не сохраняется - в рамках текущей версии база данных не используется.
Технический осмотр реализован как программная проверка характеристик транспорта. Для электрического транспорта учитывается установленный лимит энергопотребления.
В дальнейшем приложение можно расширить, например добавить сохранение данных в файл или базу данных, поиск по инвентарному номеру и изменение информации об уже добавленном имуществе.
